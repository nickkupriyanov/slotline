# Спецификация Slotline

## 1. Цель и границы

Slotline развивается как универсальная библиотека выбора времени и бронирования с реализациями для **React 18/19 и Angular 21/22**.

Проектирование ведётся для нового API. Полную совместимость с опубликованными `0.1.x` сохранять не требуется, но изменения должны сопровождаться миграцией и обновлёнными примерами.

Библиотека отвечает за:

- Выбор даты и предложения.
- Сбор и проверку данных.
- Прохождение сценария, включая разрешение незавершённой попытки бронирования.
- Запросы через адаптер.
- Состояния загрузки, ошибки и подтверждения.
- Доступность и адаптивное отображение.

Приложение и сервер отвечают за расписание, цены, вместимость, сохранение записи, отправку приглашений, управление существующими бронированиями и за сверку с сервером при неизвестном исходе.

Основные настройки по умолчанию сохраняются: тёмная тема, компактная карточка шириной 400 px, стандартная форма с именем и email, 24-часовое время и обычный сценарий бронирования.

В первую версию не входят состояния записи, не подтверждённые сервером: лист ожидания, запись, ожидающая одобрения, и другие подобные режимы. Если они понадобятся, их поведение проектируется отдельно.

## 2. Общая архитектура

### 2.1 Общий контроллер бронирования

**Почему нужен.** Сейчас модели и reducer находятся в core, а запросы, отмена загрузки и отправка — в React-hook. Копирование этой логики в Angular создаст две реализации, которые будут постепенно расходиться.

**Что сделать.** Добавить в `slotline-core` framework-free контроллер. React и Angular должны использовать один механизм работы с данными и состоянием.

**Как реализовать.**

Контроллер предоставляет:

| Интерфейс              | Назначение                                                                     |
| ---------------------- | ------------------------------------------------------------------------------ |
| `getSnapshot()`        | Получение неизменяемого снимка состояния                                       |
| `subscribe(listener)`  | Подписка с функцией отписки                                                    |
| `updateConfig(config)` | Обновление параметров приложения                                               |
| `actions`              | Выбор, изменение данных, возврат, отправка, повтор, разрешение попытки и сброс |
| `start()`              | Запуск загрузки и часов                                                        |
| `stop()`               | Отмена загрузок, остановка часов и наблюдения                                  |

Создание контроллера принимает адаптер, `mode`, начальную конфигурацию, временную опору, часы и, при восстановлении, `initialAttempt`. Создание контроллера не запускает запросы. `start()` и `stop()` идемпотентны и допускают повторное выполнение.

В контроллер переносятся:

- Загрузка доступности и слотов.
- Отмена запросов и защита от устаревших ответов.
- Проверка выбора и данных формы.
- Блокировка параллельной отправки.
- Создание снимка запроса.
- Обработка результата и ошибок.
- Управление попыткой бронирования и её разрешение.
- Управляемые и неуправляемые значения (см. 2.4).

Reducer остаётся чистым. DOM, фокус, измерение размеров и специфичные для фреймворка анимации остаются в биндингах.

Состояние изменяется синхронно до уведомления приложения. Исключение в `onBooked` не должно превращаться в ошибку создания записи или делать повторную отправку доступной.

Остановка компонента отменяет загрузки доступности, но не означает отмену уже отправленного бронирования. Поздний результат сохраняет связь с исходным запросом и не изменяет новый сценарий.

**Проверка готовности.**

- Асинхронные сценарии проверяются напрямую в core.
- Несколько экземпляров независимы.
- Повторный запуск и остановка не создают дублирующих запросов.
- Существующие проверки сброса, повторной отправки и устаревших ответов сохраняются.

### 2.2 Снимок и производная модель

`getSnapshot()` возвращает сохранённый объект и не вычисляет ничего по текущим часам:

```ts
interface BookingSnapshot {
  revision: number;
  state: Readonly<BookingState>;
  view: Readonly<BookingView>;
}
```

**Что сделать.** Добавить в core чистую функцию `deriveBookingView(state, config, anchor)`, которая использует переданную временную опору и не обращается к `Date.now()`.

Она вычисляет:

- Сетку календаря и данные дней.
- Названия месяцев и дней недели.
- Подписи даты, времени и продолжительности.
- Доступность выбора и признак недействительности управляемого выбора.
- Ошибки формы и их видимость.
- Возможность возврата, отправки, повтора и сброса.
- Логические шаги и объявления для live region.
- Резюме текущего выбора и незавершённой попытки.

**Как реализовать.**

- Контроллер кеширует результат. Ключ кеша состоит из ревизий состояния, конфигурации и временной опоры.
- Пока ключ не изменился, `getSnapshot()` возвращает тот же объект.
- Снимок не содержит функций, DOM-элементов и объектов фреймворков. Действия находятся отдельно в `controller.actions`.
- Разрешение системной темы, измерение контейнера и физический фокус остаются в UI-слое.
- Для преобразования логических шагов в прогресс компактной или расширенной компоновки используется общий чистый селектор core.
- Шаг `attempt` — служебный экран операции и не является пользовательским пунктом индикатора прогресса.
- Angular не повторяет производную логику React.

**Проверка готовности.**

- Повторные вызовы `getSnapshot()` без изменений возвращают один и тот же объект.
- Производная модель вычисляется в core и покрыта тестами core, а не биндингов.

### 2.3 Время, часы и границы

Одной календарной даты недостаточно: календарю нужна граница суток, а проверке идемпотентности — точное время истечения срока.

```ts
interface BookingTimeAnchor {
  nowMs: number;
  today: string; // YYYY-MM-DD в принятом timeZone
}

interface BookingClock {
  now(): number;
  schedule(atMs: number, callback: () => void): () => void;
}
```

Контроллер получает `initialTime` и внедряемый `clock`.

**Правила обновления.**

- При создании контроллера временная опора фиксируется.
- Контроллер планирует обновление на ближайшую значимую границу: полночь в выбранном поясе или истечение срока безопасного повтора.
- Биндинги запускают часы после клиентского подключения и останавливают при уничтожении контроллера. React Strict Mode не должен создавать дублирующиеся таймеры.
- После возвращения вкладки из фонового режима время сверяется повторно.
- Перед отправкой и перед повтором контроллер обязательно проверяет время заново: задержавшийся таймер не должен разрешать просроченный повтор.
- Смена часового пояса пересчитывает `today` из той же временной опоры и перепланирует границу суток.
- Эти таймеры обновляют состояние интерфейса и не запускают повторное бронирование.

**Для SSR.** Сервер передаёт клиенту сериализованный `initialTime`. До завершения гидратации клиент использует именно его, затем подключается реальный источник времени.

**Проверка готовности.** Управляемые часы позволяют проверить полночь, смену пояса и истечение срока без реального ожидания.

### 2.4 Управляемые и неуправляемые значения

Для всех значений действует одна модель:

| Значение       | Управляемое свойство | Начальное значение  | Событие              |
| -------------- | -------------------- | ------------------- | -------------------- |
| Выбор          | `selection`          | `defaultSelection`  | `onSelectionChange`  |
| Поля формы     | `values`             | `defaultValues`     | `onValuesChange`     |
| Длительность   | `duration`           | `defaultDuration`   | `onDurationChange`   |
| Часовой пояс   | `timeZone`           | `defaultTimeZone`   | `onTimeZoneChange`   |
| Формат времени | `timeFormat`         | `defaultTimeFormat` | `onTimeFormatChange` |

```ts
type TimeFormat = '12h' | '24h';
```

Значение по умолчанию — `'24h'`, что сохраняет прежнее отображение. Режим `locale` в первую версию не входит: приложение выбирает формат явно.

**Правила.**

- Если свойство предоставлено приложением, оно управляемое; если отсутствует — контроллер хранит значение сам и использует соответствующий `default*`.
- В управляемом режиме действие предлагает новое значение через событие, но не заменяет принятое значение оптимистично.
- В неуправляемом режиме контроллер принимает значение и уведомляет приложение.
- Внешнее обновление не вызывает повторного события изменения.
- `null` означает отсутствие выбора; `undefined` — отсутствие управляемого свойства.
- Режим каждого свойства фиксируется при создании контроллера.
- Отдельного протокола «предложение отклонено» нет: приложение сохраняет старое значение, и оно остаётся текущим.

**События изменения.** Все события изменения используют общую форму метаданных:

```ts
type SelectionChangeReason =
  | 'date-select'
  | 'slot-select'
  | 'duration-change'
  | 'time-zone-change'
  | 'context-change'
  | 'availability-change'
  | 'reset';

interface BookingChangeMetadata {
  duration: number;
  timeZone: string;
  contextKey: string;
  reason: SelectionChangeReason;
}

onSelectionChange(selection, metadata);
onDurationChange(nextDuration, metadata);
onTimeZoneChange(nextTimeZone, metadata);
onContextChange(nextContext, metadata);
```

- `onSelectionChange` работает в обоих режимах, `selection` и `booking`: приложение может отслеживать выбор до отправки записи.
- Переданное приложением значение не вызывает ответное событие с тем же значением.
- Зависимые последствия возникают после принятия изменения.
- Повторное применение одинакового обновления не создаёт повторных уведомлений.
- Если принятая длительность, пояс, контекст или новая доступность делают выбор недействительным, контроллер предлагает очистить его через `onSelectionChange` с соответствующей причиной. До принятия очистки управляемый выбор может оставаться видимым, но помечается недействительным и не допускается к отправке.
- Для аналитики успешной записи остаётся отдельный `onBooked`; событие выбора его не заменяет.

**Диагностика смены режима.** Смена режима не бросает исключение во время рендера.

- В development выдаётся однократное предупреждение с названием свойства.
- В production сохраняется первоначальный режим.
- Если свойство было неуправляемым, поздно появившееся управляемое значение игнорируется.
- Если свойство было управляемым, последующий `undefined` не переводит его в неуправляемое: сохраняется последнее принятое значение.
- Изменение `default*` после создания не переинициализирует состояние.
- Одновременная передача управляемого значения и `default*` вызывает предупреждение; управляемое значение имеет приоритет.

Паттерн `duration={draft?.duration}` прямо описывается в документации как ошибочный для асинхронной загрузки: приложение либо сразу передаёт допустимое управляемое значение, либо создаёт компонент после загрузки.

Для немедленного отклика приложение обновляет значение синхронно, а асинхронную проверку выполняет отдельно. Если нужно дождаться проверки до принятия выбора, приложение может временно установить общий `disabled`.

Эта семантика одинакова для React, Angular и headless-контроллера.

### 2.5 Шаги сценария и попытка бронирования

```ts
type SlotlineStep = 'date' | 'time' | 'details' | 'attempt' | 'confirmed';
```

Попытка бронирования хранится отдельно от редактируемого сценария: её ключ, неизменяемый запрос и момент начала. Новая намеренная операция получает новый ключ; повтор одной попытки использует прежний ключ и прежние данные.

`reset()` очищает выбор, значения и признаки взаимодействия, но **не удаляет незавершённую попытку и не разблокирует новую отправку**.

Если попытка выполняется или имеет неизвестный исход:

- Её ключ и снимок запроса сохраняются.
- Виджет показывает экран `attempt`.
- Новый `submit()` не создаёт другую попытку.
- Повтор неизвестной операции использует прежний ключ.
- Сброс не трактуется как отмена серверной записи.

Показывать календарь с незаметным баннером не следует: пользователь должен видеть, что прежняя операция ещё не разрешена. «Book another» появляется только после известного успешного результата.

После `resolveAttempt({ outcome: { status: 'not_created' } })` контроллер возвращается к подходящему шагу. Если черновик уже сброшен — к выбору даты. При подтверждённом создании показывается результат; новое бронирование начинается отдельным действием.

**Восстановление попытки.**

```ts
interface InitialBookingAttempt {
  idempotencyKey: string;
  request: Readonly<BookingRequest>;
  startedAt: number; // Unix time, миллисекунды
  status: 'pending' | 'unknown';
}
```

Восстановленный `pending` нормализуется в `unknown`: новый контроллер не владеет исходным сетевым запросом и не может утверждать, что тот продолжает выполняться. Восстановленная незавершённая попытка получает состояние `unknown`; запрос самопроизвольно не повторяется.

Сохранение этой информации между перезагрузками контролирует приложение. Встроенной записи контактных данных в `localStorage` не будет.

**Редактирование и следующая отправка.**

| Состояние                           | Редактирование                           | Следующая отправка                                 |
| ----------------------------------- | ---------------------------------------- | -------------------------------------------------- |
| Запрос выполняется                  | Заблокировано в интерфейсе               | Повторный вызов не отправляется                    |
| Исход неизвестен                    | Показывается неизменяемое резюме попытки | Прежний запрос и ключ, если повтор безопасен       |
| Сервер подтвердил отсутствие записи | Разрешено                                | Новая попытка с актуальными данными и новым ключом |
| Запись создана                      | Экран результата                         | Новая операция через «Book another»                |

При `TEMPORARY_FAILURE`, `VALIDATION_FAILED`, `SLOT_UNAVAILABLE` и `GENERIC_FAILURE` предыдущая попытка завершена; исправления пользователя не игнорируются.

Внешние управляемые значения могут обновиться даже во время отправки, но не меняют сохранённый запрос. Пока исход неизвестен, интерфейс показывает сведения именно отправленной попытки, и новый черновик нельзя отправить до разрешения старой операции.

**Экран незавершённой попытки.**

| Состояние попытки               | Что показывается                                          | Какие действия доступны                                                                       |
| ------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `pending`                       | Резюме отправленного запроса и индикатор выполнения       | Новая отправка и редактирование недоступны                                                    |
| `unknown`                       | Резюме, сообщение о возможном создании записи, инструкция | Безопасный повтор, если разрешён; действие проверки статуса, если его предоставило приложение |
| Известно, что запись не создана | Форма или предыдущий допустимый шаг с ошибкой             | Исправление данных и новая попытка                                                            |
| Запись создана                  | Подтверждение                                             | Действия подтверждения и новая запись                                                         |

Экран собирается из заменяемых частей: `Attempt` получает замороженное резюме запроса, статус попытки и допустимые действия; само резюме может использовать общую часть `Summary`.

**Проверка готовности.**

- Сброс во время незавершённой попытки не разблокирует отправку и не создаёт второй запрос.
- Восстановление `initialAttempt` даёт состояние `unknown` и не повторяет запрос автоматически.
- Истечение срока не разрешает новую попытку, пока исход неизвестен.

## 3. Улучшения

### 1. Поддержка Angular

**Почему нужна.** Angular — целевая платформа библиотеки. Общий контроллер позволяет добавить её без повторной реализации бизнес-логики.

**Что сделать.** Добавить `@nickkupriyanov/slotline-angular`:

- Standalone-компонент готового виджета.
- Headless-сервис.
- Настройку темы, классов, локали, продолжительности и пояса.
- События выбора, результата и ошибки.
- Доступный календарь, форму и подтверждение.

**Точки входа.**

```text
@nickkupriyanov/slotline-angular          компонент, headless-сервис, template-директивы
@nickkupriyanov/slotline-angular/forms    директива ControlValueAccessor
@nickkupriyanov/slotline-angular/styles.css
```

`@angular/forms` объявляется необязательным peer и используется только подпутём `/forms`; главная точка входа его не импортирует.

**Как реализовать.**

- Один экземпляр компонента использует один контроллер.
- Сервис отображает снимки контроллера в readonly signals.
- Компоненты используют `OnPush`.
- Inputs передаются в `updateConfig`, outputs сообщают приложению о событиях.
- Подписки, часы и загрузки освобождаются при уничтожении.
- Используются стили и CSS-классы core; общий stylesheet копируется в публикуемый Angular-пакет по аналогии с React.
- Angular-компоненты не содержат отдельной копии визуальных component styles. Используется `ViewEncapsulation.None`; правила ограничены префиксом Slotline.
- Клавиатура, фокус и live region реализуются в Angular-биндинге.
- Angular Material не становится обязательной зависимостью.
- Базовые анимации используют общий CSS; Motion остаётся расширением React.

Библиотеку собирать средствами Angular 21 с partial compilation (`@angular/compiler-cli` 21.2.0, `ng-packagr` 21.2.7, TypeScript 5.9.3). Проверять установку в отдельных приложениях Angular 21 и 22. Публичные peer ranges библиотеки остаются диапазонами поддержки Angular 21/22.

**Тестирование.**

- Angular unit-тесты: Angular CLI test builder, TestBed и Vitest 4.0.8.
- Core и React сохраняют Vitest 5.
- Оба Angular-приложения проверяются в zoneless-режиме и с `zone.js`.
- Для Angular 21 и 22 обязательны серверный рендер и браузерная гидратация с `provideClientHydration`.
- Отдельно проверяется CVA: `writeValue`, change, touched, disabled и отсутствие обратных циклов.

**Проверка готовности.** Один адаптер работает в обеих библиотеках. Выбор, ошибка, повтор, сброс и подтверждение имеют одинаковую семантику. Angular-пакет устанавливается из tarball и проходит SSR-проверку.

### 2. Настраиваемая форма

**Почему нужна.** Обязательные имя и email ограничивают использование компонента для услуг, консультаций и записи по телефону.

**Что сделать.** Добавить:

- `fields` — конфигурацию встроенной формы.
- `defaultValues` — начальные значения.
- `values` и `onValuesChange` — управление значениями извне.
- `validateValues` — собственную проверку.
- Возможность полностью заменить форму.

**Как реализовать.**

Данные формы становятся типизированным объектом. Ошибки и отметки взаимодействия хранятся по именам полей.

Встроенные типы:

- Text и textarea.
- Email и телефон.
- Number.
- Select.
- Checkbox.

Поле описывает имя, подпись, пояснение, обязательность, варианты выбора и правила проверки. Порядок конфигурации определяет порядок отображения.

Стандартная конфигурация остаётся «имя + email». Разработчик может убрать email или заменить весь набор полей.

Начальные значения применяются при создании сценария. Изменение конфигурации не перезаписывает пользовательский ввод. `reset()` восстанавливает актуальные начальные значения.

Смена слота, возврат и ошибка отправки сохраняют форму. Серверные ошибки появляются рядом с соответствующими полями и снимаются при изменении значения. Ошибки для полей, неизвестных форме, дополнительно отображаются в общей области, чтобы сообщение не потерялось.

Пользовательская форма работает через те же значения, ошибки и действия. Core выполняет проверку перед отправкой независимо от того, каким интерфейсом собраны данные.

В первой версии встроенные поля работают со скалярными значениями. Вложенные структуры и сложные анкеты реализуются пользовательской формой.

**Проверка готовности.**

- Можно собрать форму без email, добавить обязательный вопрос, предзаполнить данные и связать серверную ошибку с полем.
- Несколько виджетов не конфликтуют через идентификаторы элементов.

### 3. Замена частей интерфейса

**Почему нужна.** Изменение одной карточки или формы не должно требовать переписывания всего виджета.

**Что сделать.** Добавить единую систему точек расширения:

```text
Header
Progress
DayContent
Slot
Form
Summary
Attempt
Confirmation
DurationFooter
Loading
Error
Empty
```

`Summary` используется и перед формой, и при `formMode: 'skip'`. `Attempt` обслуживает экран незавершённой попытки. `DurationFooter` не управляет продолжительностью самостоятельно — вызывает подготовленное действие контроллера.

Экспортировать стандартные части для композиции.

**Как реализовать.**

React получает карту `components`. Angular получает template-директивы с эквивалентными контекстами.

Пользовательская часть получает только необходимые данные и действия. Например, слот получает предложение, форматированное время, состояние выбора и подготовленные атрибуты кнопки.

`DayContent` заменяет содержимое дня внутри стандартной интерактивной оболочки. Управление фокусом и клавиатурой сохраняется в библиотеке.

Полная замена слота получает обработчики и доступные атрибуты, которые нужно передать собственному элементу. Документация показывает этот контракт.

Стандартные части можно оборачивать и дополнять. `classNames` продолжает работать независимо.

Карта `components` сосуществует с провайдером: `components` настраивает стандартный виджет, provider и hooks позволяют собрать полностью свой интерфейс. Контроллер, значения и валидация в обоих случаях одни.

Конфигурация полей и замена формы используют один механизм данных и проверки. Отдельной системы состояния для пользовательской формы не появляется.

Полная замена календарного поведения в этот механизм не входит: для неё используется headless-интерфейс.

**Проверка готовности.**

- Можно независимо заменить форму, подтверждение и экран попытки, добавить специалиста или цену в слот.
- Частичная настройка сохраняет доступность, а требования к полной замене документированы.

### 4. Режим выбора даты и времени

**Почему нужен.** Он позволяет использовать Slotline внутри checkout, существующей формы или многошагового процесса.

**Что сделать.** Добавить:

- `mode: 'booking' | 'selection'`.
- `selection`.
- `defaultSelection`.
- `onSelectionChange`.

По умолчанию используется `booking`.

Выбор представлен одним атомарным значением:

```ts
type BookingSelection = {
  date: string;
  slot: TimeSlot | null;
} | null;
```

**Как реализовать.**

Продолжительность нужна в обоих режимах и остаётся отдельным параметром: `duration`, `defaultDuration`, `onDurationChange`, `durations`, `showDurationSelector` (по умолчанию `true`). Футер продолжительности не относится к форме контактов и сохраняется в режиме `selection`. При одной доступной продолжительности переключатель можно скрыть. В `BookingSelection` продолжительность не дублируется.

Событие выбора получает метаданные:

```ts
onSelectionChange(selection, metadata);
```

Форма метаданных и закрытый список причин изменения — в 2.4.

В режиме `selection`:

- Достаточно адаптера доступности и слотов.
- `createBooking` не требуется и не вызывается.
- Форма и подтверждение записи отсутствуют.
- Выбранный слот остаётся выделенным.
- Приложение получает предложение целиком.

Предустановленный слот проверяется по актуальной доступности. Непроверенный или недоступный выбор нельзя использовать для отправки. При смене продолжительности прежний слот проходит инвалидирование; отправка блокируется до нового подтверждённого выбора.

**Адаптеры разделяются.**

```ts
interface AvailabilityAdapter {
  getAvailability(query: AvailabilityQuery): Promise<DayAvailability[]>;
  getSlots(query: SlotsQuery): Promise<TimeSlot[]>;
}

interface BookingAdapter extends AvailabilityAdapter {
  createBooking(request: BookingRequest): Promise<BookingResult>;
  capabilities?: BookingCapabilities;
}
```

Конфигурация контроллера — discriminated union по `mode`: `selection` принимает `AvailabilityAdapter`, `booking` требует `BookingAdapter`. `createBooking` не становится опциональным методом общего адаптера, поэтому потребителю режима выбора не нужна заглушка.

В режиме бронирования добавить `formMode: 'collect' | 'skip'`. При пропуске формы необходимые данные предоставляет приложение. Перед созданием записи остаётся резюме с явной кнопкой подтверждения.

Индикатор прогресса формируется из фактических этапов. Произвольный конструктор шагов не добавляется; служебный шаг `attempt` в прогресс не входит.

В Angular режим выбора подключается к Angular Forms через отдельную директиву `ControlValueAccessor` в подпути `/forms`. Она обрабатывает значение, touched и disabled.

**Проверка готовности.**

- Slotline работает как поле чужой формы, не создаёт вложенную форму и не отправляет запись при выборе времени.
- Управляемый сброс и недоступный начальный выбор обрабатываются корректно.

### 5. Данные предложения и контекст

**Почему нужны.** В одно время могут быть доступны разные специалисты или ресурсы. Время начала не обеспечивает идентичность предложения.

**Что сделать.** Новый `TimeSlot` содержит:

- Обязательный `id`.
- `start`.
- Необязательный `end`.
- Типизированный `data`.

Контекст содержит `key` и типизированный `data`.

**Как реализовать.**

- Выбор, ключи элементов и восстановление предложения используют `id`.
- Идентификатор устойчив внутри контекста и не меняется при смене пояса.
- Цена, специалист, кабинет и вместимость находятся в `data`.
- Контекст передаётся во все запросы адаптера.
- Изменение `context.key` означает новое расписание.
- При смене контекста загрузки отменяются, доступность и выбор очищаются, форма сохраняется.
- Старые ответы не изменяют новый контекст.
- После повторной загрузки выбранное предложение сверяется с актуальными данными.
- Дублирующиеся идентификаторы и некорректные времена диагностируются как `ADAPTER_CONTRACT_VIOLATION` (см. 6).

`onContextChange(nextContext, metadata)` сообщает приложению о смене контекста с теми же метаданными, что и остальные события изменения (см. 2.4).

Типы данных слота, формы, контекста и результата выводятся из адаптера. Простое использование не требует явного перечисления всех generic-параметров.

**Проверка готовности.**

- Два предложения в одно время различимы.
- Смена услуги не сохраняет старый слот.
- Дополнительные данные не теряются при выборе и отправке.

### 6. Ошибки и безопасные повторы

**Почему нужны.** Занятый слот, неверное поле и потерянный ответ требуют разного восстановления. Клиентская блокировка параллельных вызовов не гарантирует серверную идемпотентность.

**Форма ошибки.** `BookingError` — экспортируемый runtime-класс, который бросает адаптер:

```ts
new BookingError({
  code: 'VALIDATION_FAILED',
  message: 'Проверьте данные',
  fieldErrors: { phone: 'Неверный номер' },
  cause,
});
```

Предоставляются `isBookingError()` и нормализация неизвестных исключений. Проверка не ограничивается `instanceof`, чтобы работать при нескольких копиях пакета.

| Код                          | Значение                                           |
| ---------------------------- | -------------------------------------------------- |
| `SLOT_UNAVAILABLE`           | Предложение недоступно, запись не создана          |
| `VALIDATION_FAILED`          | Данные отклонены, запись не создана                |
| `TEMPORARY_FAILURE`          | Временный отказ с гарантией, что запись не создана |
| `GENERIC_FAILURE`            | Другой подтверждённый отказ без создания записи    |
| `UNKNOWN_OUTCOME`            | Нельзя установить результат создания               |
| `ADAPTER_CONTRACT_VIOLATION` | Некорректные данные или результат адаптера         |

Гарантию «не создана» адаптер выражает соответствующей категорией. Если такой гарантии нет, используется `UNKNOWN_OUTCOME`. Обычное неклассифицированное исключение при создании трактуется как неизвестный исход.

При нарушении контракта важна фаза:

- Некорректная доступность или слоты — ошибка данных, создание ещё не выполнялось.
- Некорректный ответ `createBooking` — исход потенциально неизвестен. Новый запрос автоматически не разрешается.

**Уведомление приложения.**

```ts
onError(error, {
  phase: 'availability' | 'slots' | 'booking',
  outcome: 'not_created' | 'unknown' | 'not_applicable',
  request,
});
```

`onError` вызывается и для ожидаемых отказов, включая занятый слот. Отменённая библиотекой загрузка ошибкой не считается и `onError` не вызывает.

**Идемпотентность.** Каждый запрос создания получает обязательный `idempotencyKey` в `BookingRequest`. Способность адаптера описывается объединением:

```ts
type BookingCapabilities =
  | { idempotentCreate?: false; idempotencyRetentionMs?: never }
  | { idempotentCreate: true; idempotencyRetentionMs: number };
```

По умолчанию `idempotentCreate` — `false`. При `true` адаптер обязан указать срок гарантированного хранения ключа; контроллер не предлагает повтор неизвестной операции после истечения этого срока.

**Контракт безопасного повтора.**

- `startedAt` фиксируется перед первой отправкой.
- Повтор не обновляет `startedAt`.
- Ключ и полезная нагрузка остаются прежними.
- Повтор разрешён только при `nowMs < startedAt + idempotencyRetentionMs`.
- На самой границе срока повтор уже запрещён.
- Истечение срока запрещает повтор, но не разрешает новую попытку: неизвестный исход всё ещё нужно установить.
- Адаптер гарантирует, что повтор того же запроса в указанном окне не создаст вторую запись.
- Приложение восстанавливает попытку с адаптером того же серверного назначения.

В runtime структурно проверяются capabilities, положительный конечный срок, корректность времени и соответствие ключа запросу. `instanceof` для этого не используется. Источник времени общий с контроллером; в пределах жизни контроллера перевод часов назад не продлевает разрешённое окно. Если после восстановления время противоречит `startedAt`, безопасный повтор отключается до проверки исхода или устранения некорректных данных.

**Поведение по категориям.**

- Занятый слот: обновить доступность, убрать выбор времени, сохранить форму.
- Ошибка полей: оставить форму и показать ошибки.
- Временный отказ: сохранить данные и предложить повтор.
- Неизвестный исход: перейти на экран `attempt`, разрешить повтор только при заявленной серверной идемпотентности.

Ошибки загрузки доступности можно повторять независимо. Автоматические повторы по таймеру не добавляются. Сохранение попытки между перезагрузками страницы остаётся ответственностью приложения.

**`resolveAttempt`.**

```ts
resolveAttempt({
  idempotencyKey,
  outcome:
    | { status: 'created'; result: BookingResult }
    | { status: 'not_created' }
    | { status: 'unknown' },
}): boolean;
```

- `created` завершает попытку, вызывает `onBooked` один раз и показывает подтверждение, если её сценарий ещё актуален.
- `not_created` окончательно закрывает попытку и разрешает новую отправку с новым ключом. Это означает окончательное серверное решение: исходная операция уже не может позднее создать запись.
- `unknown` сохраняет блокировку.
- Несовпадающий ключ или повторное разрешение завершённой попытки возвращает `false` без изменения состояния.

**Проверка готовности.**

- Проверены конфликт, ошибка поля, потеря ответа после создания записи, повтор с прежним ключом и отсутствие серверной поддержки.
- Интерфейс не объявляет запись неуспешной, когда её исход неизвестен.
- Проверено, что исключение в `onBooked` не превращает созданную запись в ошибку.

### 7. Расширенное подтверждение

**Почему нужно.** После записи пользователю нужны статус и инструкции. Сообщение об отправке приглашения должно соответствовать фактическому результату.

**Что сделать.** `BookingResult` содержит обязательные поля созданной записи:

```ts
interface BookingResult {
  id: string; // идентификатор созданной записи, не слота
  status: 'confirmed';
  // Остальные согласованные поля результата.
}
```

Разграничение идентификаторов:

- `TimeSlot.id` идентифицирует доступный интервал.
- `BookingResult.id` идентифицирует созданную запись.
- `idempotencyKey` идентифицирует попытку создания.

`status: 'confirmed'` означает подтверждённое создание записи. Статус отправки приглашения описывается отдельно и не смешивается с ним.

Серверный ответ вида `{ ok: true }` этому контракту не соответствует. Адаптер должен получить идентификатор созданной записи из ответа или предусмотренной сервером операции проверки. Генерировать фиктивный идентификатор на клиенте нельзя.

Дополнительно результат содержит:

- Явный статус приглашения и адрес получателя.
- Место встречи и инструкции.
- URL подключения.
- URL календаря.
- URL переноса и отмены.

**Как реализовать.**

Подтверждение использует снимок отправленного запроса и результат адаптера. Изменение текущей формы не меняет сведения созданной записи.

Приглашение показывается как отправленное только при явном статусе `sent`; для статусов ожидания и отказа используются отдельные тексты (см. раздел 4).

Действия появляются только при наличии соответствующих данных. Перенос и отмена открывают интерфейс приложения — методы изменения записи в адаптер не добавляются.

Первое действие «Добавить в календарь» использует предоставленный URL. Генерация ICS не входит в этот выпуск.

Стандартное подтверждение можно заменить через систему компонентов.

**Проверка готовности.**

- Корректны онлайн-встреча, очная запись и разные статусы приглашения.
- Отсутствующие данные не оставляют пустые блоки.
- Сброс из callback результата корректно возвращает начальный экран.
- `resolveAttempt({ status: 'created', result })` подчиняется тем же требованиям к обязательным полям.

### 8. Адаптация к контейнеру

**Почему нужна.** Узкая панель на широком экране требует компактного интерфейса. Текущая стабильная ширина карточки должна сохраниться.

**Что сделать.** Перевести адаптацию содержимого на container queries. Расширенную компоновку включать явно.

**Токены.**

```css
--sl-width: 400px;
--sl-width-adaptive: 800px;
--sl-max-height: none;
```

**Носитель режима.** Корень получает `data-sl-layout="compact"` или `data-sl-layout="adaptive"`. Атрибут отражает выбранный режим компонента и определяет токен желаемой ширины: `compact` → `--sl-width`, `adaptive` → `--sl-width-adaptive`. В обоих случаях ширина ограничивается родителем.

**Как реализовать.**

- Создать именованный контейнер и адаптировать внутренние элементы. Контейнерные правила применяются к потомкам контейнера; нельзя пытаться менять сам контейнер через его собственный size query.
- В режиме `adaptive` при фактической ширине карточки менее 720 px содержимое остаётся в одну колонку; начиная с 720 px используется двухколоночная композиция (календарь и слоты рядом). Атрибут при этом не переключается обратно в `compact`, поэтому измерение собственной ширины не создаёт колебаний между режимами.
- Обеспечить перенос подписей, действий и длинных значений.
- Автоматическое число колонок слотов вычисляется через отдельную внутреннюю переменную: до 300 px включительно — одна, до 380 px включительно — две, выше — три.
- Пользовательский `--sl-slot-columns` имеет приоритет: итоговое правило использует пользовательский токен, если он задан, иначе автоматическое значение. Container query не переопределяет публичный токен на дочернем элементе.
- Ограничение высоты задаётся только `--sl-max-height`; отдельного `maxHeight` prop нет. При ограниченной высоте центральная область прокручивается, сохраняя доступность действий. Прокрутка реализуется семантической областью с доступным названием текущего шага.
- Выпадающие элементы, которым необходимо выходить за границы карточки, размещаются через предусмотренный overlay/portal-механизм.

Изменение размеров:

- Не сбрасывает данные.
- Не вызывает загрузку.
- Не меняет выбранное предложение.
- Не оставляет скрытые элементы в Tab-навигации.
- Сохраняет логичный фокус.

Логика размеров принадлежит UI-биндингу. Контроллер не зависит от DOM.

**Проверка готовности.**

В реальном браузере проверены контейнеры 280, 320, 400 и 800 px, широкое окно с узкой панелью, оба языка, увеличение масштаба и переходы между компоновками. Дополнительно проверяются:

- Отсутствие горизонтального переполнения.
- Прокрутка центральной области при `--sl-max-height`.
- Доступность всех элементов с клавиатуры.
- Видимость `:focus-visible`.
- Корректное положение абсолютных элементов (containment не должен ломать позиционирование).
- Отсутствие изменения ширины между шагами.
- Поведение overlay/portal в модальном окне, включая фокус и порядок слоёв.
- Приоритет пользовательского `--sl-slot-columns`.

### 9. Выбор часового пояса

**Почему нужен.** Клиент и организатор могут находиться в разных странах. Пояс должен быть понятен на всех этапах.

**Что сделать.** Сначала обеспечить согласованность при внешней смене пояса, затем добавить:

- `defaultTimeZone`.
- Управляемый `timeZone`.
- `onTimeZoneChange`.
- `showTimeZoneSelector`.
- Необязательный список `timeZones`.

**Как реализовать.**

`timeZone` определяет отображение и календарные запросы. Рабочий пояс расписания определяет сервер.

При смене пояса:

1. Отменяются старые загрузки.
2. Дата выбранного предложения вычисляется из `slot.start` в новом поясе.
3. Обновляются дата и месяц календаря, `today` пересчитывается из той же временной опоры, граница суток перепланируется.
4. Предложение проверяется по актуальной доступности.
5. До окончания проверки отправка блокируется.

Если предложение доступно и входит в ограничения дат, сохраняются его идентификатор и реальный момент. Иначе контроллер предлагает очистить выбор через `onSelectionChange` с причиной `time-zone-change`: до принятия очистки управляемый выбор может оставаться видимым, но помечается недействительным и не допускается к отправке. Форма сохраняется.

Во время отправки встроенный переключатель заблокирован. Внешнее обновление пояса не изменяет уже отправленный снимок запроса.

При отсутствии заданного списка используются поддерживаемые системой пояса с добавлением UTC и текущего пояса. Если перечисление недоступно, доступны UTC и текущий пояс.

Поиск выполняется локально. Смещение рассчитывается для даты встречи. При повторяющемся локальном времени рядом со слотом показывается смещение.

**Проверка готовности.**

Проверены соседний календарный день, сезонные переходы, повторяющееся локальное время, быстрые переключения и отсутствие прежнего предложения после обновления.

### 10. Формат 12/24 часа

**Почему нужен.** Формат зависит от аудитории и не всегда совпадает с языком интерфейса.

**Что сделать.** Добавить `timeFormat: '12h' | '24h'` с парами `defaultTimeFormat` и `onTimeFormatChange`, по умолчанию `24h`. Предусмотреть необязательный переключатель и уведомление об изменении.

Режим `locale` в первую версию не входит: формат выбирается явно. Обозначения части суток формирует `Intl`.

**Как реализовать.**

Общий форматтер принимает настройку: `24h` — `h23`, `12h` — `h12`. Один формат используется в слотах, резюме, подтверждении и доступных подписях.

Переключение меняет только представление: выбор, форма и доступность остаются прежними. Запросы не выполняются. Предпочтения экземпляров независимы.

**Проверка готовности.**

Корректны полночь, полдень и вечернее время. Формат согласован на всех экранах, длинные подписи помещаются в компактной карточке.

## 6. Framework-free DOM-подпуть

Отдельный npm-пакет для DOM не создаётся. В core добавляется изолированный подпуть:

```text
@nickkupriyanov/slotline-core/dom
```

В нём находятся framework-free утилиты:

- Наблюдение за размером элемента.
- Наблюдение за media query.
- Поиск фактически доступных для фокуса элементов.
- Ловушка фокуса и освобождение обработчиков.
- Общая механика измерения и анимации высоты.

Главная точка входа core не импортирует DOM-подпуть. Импорт `/dom` не обращается к `window` или `document` до вызова функций.

React hooks и Angular-сервис связывают эти утилиты с жизненным циклом фреймворка. Дублируется только тонкая интеграция. `useControllableState` для доменных значений заменяется общей логикой контроллера.

## 7. Последовательность реализации

| Этап                              | Содержание                                                                                                                     | Условие завершения                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| **A. Корректность**               | Дата и пояс, достоверное приглашение                                                                                           | Проверки покрывают исправленные сценарии                     |
| **B. Общая основа**               | Контроллер, снимок и временная опора, новые модели, идентичность слота, базовый контракт ошибок, безопасной отправки и попытки | Core работает без React; React переведён на контроллер       |
| **C. Angular**                    | Готовый виджет и headless-сервис                                                                                               | Паритет текущего сценария; установка в Angular 21/22         |
| **D. Выбор внутри приложения**    | Управляемый выбор, selection, пропуск формы, Angular Forms                                                                     | Работают законченные примеры внешней формы                   |
| **E. Расширяемость**              | Настраиваемые поля, замена частей, контекст и данные                                                                           | Примеры разных услуг и ресурсов работают в обеих библиотеках |
| **F. Восстановление и результат** | Полный интерфейс ошибок и экрана попытки, разрешение неизвестного исхода, расширенное подтверждение                            | Проверены реалистичные отказы и повторы                      |
| **G. Интерфейс**                  | Компактная адаптация, 12/24, переключатель пояса, расширенная компоновка                                                       | Пройдены браузерные проверки                                 |

Этап A — регрессионные проверки корректности новой линии, а не отдельный выпуск старого API. Последовательность: зафиксировать воспроизводимые сценарии, перенести поведение в общий контроллер, реализовать исправления там, проверить биндинги. Исправления не пишутся дважды; отдельная поддержка ветки `0.1.x` не требуется.

Уже в базовом выпуске результат содержит обязательные `id` и `status`, а информация о приглашении — явный статус. Приглашение показывается только при `invitation.status === 'sent'`; при отсутствии статуса строка скрыта. Этап F добавляет адрес, инструкции, ссылки и расширенный интерфейс восстановления; достоверность базового подтверждения до него не откладывается.

Базовые правила идемпотентности и неизвестного исхода, временная опора и разделение шага `attempt` входят в общую основу. Их нельзя откладывать до этапа F, оставляя промежуточный новый API небезопасным.

Компактную адаптацию и 12/24 можно реализовать раньше других интерфейсных расширений. Если они выпускаются отдельно, версии последующих релизов пересчитываются по правилам раздела 8.

## 8. Версионирование

### Правила бампа

До `1.0.0` действует следующая политика проекта:

| Изменение                                                          | Бамп                                                      |
| ------------------------------------------------------------------ | --------------------------------------------------------- |
| Исправление без изменения публичного контракта                     | `patch`                                                   |
| Новая публичная возможность                                        | `minor`                                                   |
| Несовместимое изменение API                                        | `minor` с миграцией и отметкой breaking change            |
| Внутренний рефакторинг публикуемого пакета без изменения поведения | `patch`                                                   |
| Изменение только CI, инструментов или playground                   | Без бампа библиотек                                       |
| Изменение README внутри публикуемого пакета                        | `patch`                                                   |
| Изменение общего CSS                                               | Релиз каждого биндинга, в чей tarball этот CSS копируется |

В Changesets до `1.0.0` для несовместимого изменения выбирается `minor`: `major` поднял бы пакет до `1.0.0`, чего на этом этапе делать не требуется.

После `1.0.0`: исправления — patch, совместимые возможности — minor, несовместимые изменения — major.

Изменение обязательных полей, экспортов и наблюдаемой семантики до `1.0` требует minor-релиза и описанной миграции. Добавление поля в объект запроса само по себе не ломает JavaScript-функцию адаптера, но изменения обязательных моделей всё равно требуют миграции.

### Запланированные выпуски

Текущая база: core `0.1.0`, React `0.1.1`.

Все запланированные изменения развиваются в новой линии. Отдельный выпуск исправлений для `0.1.x` не обязателен, поскольку существующих потребителей нет.

| Выпуск                             | Содержание                                                                                |    Core |   React | Angular |
| ---------------------------------- | ----------------------------------------------------------------------------------------- | ------: | ------: | ------: |
| **Новая основа**                   | Этапы A–C: контроллер, снимок и временная опора, новые базовые контракты, базовый Angular | `0.2.0` | `0.2.0` | `0.1.0` |
| **Выбор внутри приложения**        | Этап D                                                                                    | `0.3.0` | `0.3.0` | `0.2.0` |
| **Расширяемость**                  | Этап E                                                                                    | `0.4.0` | `0.4.0` | `0.3.0` |
| **Восстановление и подтверждение** | Этап F                                                                                    | `0.5.0` | `0.5.0` | `0.4.0` |
| **Интерфейсные возможности**       | Этап G                                                                                    | `0.6.0` | `0.6.0` | `0.5.0` |

Это целевые номера при указанной группировке, а не требование всегда синхронизировать номера. Если появляется дополнительный функциональный выпуск, следующие minor-номера сдвигаются. Патчи между выпусками не меняют следующий minor: например, после `0.3.2` идёт `0.4.0`.

Пакеты остаются независимо версионируемыми (`fixed: []`, `linked: []`). Исправление только React повышает только React. Если обновление core выходит за диапазон зависимости биндинга, биндинг получает обновление зависимости и собственный релиз.

### Когда менять версии

- Changeset добавляется в PR, который изменяет публикуемый пакет.
- Обычные версии в `package.json` вручную в feature-PR не меняются.
- Для завершённого набора изменений Changesets формирует version PR.
- Version PR содержит версии, changelog и обновлённые зависимости.
- Он мержится после проверок установки, сборок, тестов и документации.
- Публикация происходит из подготовленного version PR, а не из произвольного рабочего состояния.

### Предварительные версии

Новый API разрабатывается на ветке `slotline-next-api`.

Для core и React используются:

```text
0.2.0-next.0
0.2.0-next.1
0.2.0-next.2
…
0.2.0
```

Предрелизы публикуются под тегом `next`; стабильный `latest` сохраняет предыдущую версию до готовности нового выпуска.

Для ветки настраивается отдельный prerelease-процесс Changesets; существующего `release.yml`, слушающего только `main`, недостаточно. На ветке Changesets использует соответствующий `baseBranch`, core и React публикуются под `next`, Angular остаётся private и проверяется tarball. Перед выходом из prerelease возвращаются обычные настройки базовой ветки и выполняются `pre exit` и versioning.

Angular до первого готового выпуска остаётся непубликуемым пакетом. В стабильном version PR он становится публичным с начальной версией `0.1.0`. Это исключает случайную первую публикацию Angular prerelease под `latest`.

### Условия для 1.0.0

Версия `1.0.0` не привязана к завершению последней строки списка. Она выпускается, когда:

- Публичные модели и события зафиксированы.
- Согласованы правила управляемого состояния.
- Стабильны контракт ошибок и семантика повторов.
- Обе реализации проходят общие сценарии.
- Проверены установки из npm-пакетов и SSR.
- Подготовлены документация и миграции.
- Есть законченные интеграции, проверяющие API вне playground.

При первом стабильном выпуске можно привести все три пакета к `1.0.0`. После этого независимое версионирование сохраняется.

### Среда разработки

```json
{
  "engines": {
    "node": "^24.15.0 || ^26.0.0"
  }
}
```

Node 26 включается в обязательную проверку совместимости. Диапазон `>=26.0.0` не фиксируется: он заранее разрешил бы непроверенные будущие мажоры. Ограничение инструментов разработки не переносится автоматически в runtime-требования публикуемого core.

## 9. Проверки и документация

### Общие проверки

Существующие 69 тестов сохраняются или переносятся в соответствующий слой без потери проверяемого поведения.

В core проверяются:

- Токены загрузки и отмена.
- Повторный выбор той же даты.
- Сброс во время отправки.
- Изменение контекста и пояса.
- Старые успешные и ошибочные ответы.
- Идентичность предложений.
- Проверка данных формы.
- Блокировка параллельной отправки.
- Повторы и неизвестный исход.
- Тождество снимка при неизменных ревизиях и временной опоре.
- Полночь, смена пояса и истечение срока безопасного повтора через управляемые часы.
- Разделение сброса сценария и разрешения попытки.
- Диагностика фиксированного режима controlled/uncontrolled.

В биндингах проверяются:

- Отображение состояний, включая экран `attempt`.
- Фокус и клавиатурная навигация.
- Live region.
- Управляемые значения и отсутствие циклов событий.
- Подключение пользовательских частей.
- Изоляция нескольких виджетов.
- Жизненный цикл, SSR и гидратация.
- `ControlValueAccessor`: значение, touched, disabled, отсутствие обратных циклов.

Браузерная проверка охватывает:

- Узкие и широкие контейнеры.
- Все этапы и режимы.
- Русские и английские подписи.
- Форматы времени.
- Масштабирование.
- Прокрутку модального размещения.
- Reduced motion.
- Перестроение без потери фокуса.
- Отсутствие горизонтального переполнения, видимость `:focus-visible`, корректное положение абсолютных элементов.
- Поведение overlay/portal в модальном окне.
- Компактную и расширенную компоновку отдельно и в обоих фреймворках.

Матрица CI:

1. Общая job проверяет core и биндинги, собирает библиотеки и сохраняет tarball-артефакты.
2. Независимые consumer jobs устанавливают эти tarball-файлы вне workspace.
3. React проверяется в версиях 18 и 19.
4. Angular проверяется в версиях 21 и 22, в обоих режимах change detection.
5. В каждой consumer job выполняются production build и относящиеся к ней проверки SSR/гидратации и браузерного поведения.
6. Все обязательные jobs выполняются на каждом PR и повторяются на version PR.
7. Cache keys включают шаблон, режим, Node и lockfile. Один изменяемый `.verify/npm-cache` не используется всеми прогонами.

В обоих Angular-шаблонах zoneless явно включается через `provideZonelessChangeDetection()`. В конфигурации с `zone.js` загружается `zone.js` и явно используется `provideZoneChangeDetection()`.

Проверяются экспортные точки, зависимости на core, stylesheet и необязательность Motion. Версии и имена tarball выводятся из манифестов, а не фиксируются в инструментах.

### SSR

SSR обязателен для обоих биндингов. React проверяется через `renderToString` и последующий `hydrateRoot` в браузере. Angular — через серверный рендер и клиентскую гидратацию.

Условия:

- Контроллер не запускает запросы при создании.
- Server и client получают одинаковые начальные параметры и временную опору.
- Автоопределение браузерного языка, пояса и системной темы выполняется после гидратации.
- Нет обращений к DOM при серверном импорте.
- Нет предупреждений о несовпадении разметки.

### Примеры

React playground сохраняется. Angular-примеры добавляются в `apps/playground-angular` и публикуются Pages под `/angular/`. Отдельный Angular Storybook в первую версию не входит; React Storybook сохраняется под `/storybook/`. Angular playground содержит галерею состояний и примеры замены частей.

Для обоих фреймворков подготовить:

1. Стандартное бронирование.
2. Выбор времени внутри существующей формы.
3. Форму с телефоном и дополнительным вопросом.
4. Два ресурса с одинаковым временем.
5. Пользовательскую карточку слота.
6. Конфликт занятого времени.
7. Неизвестный результат и безопасный повтор.
8. Разные контейнеры, пояса и форматы времени.

Предоставить небольшой учебный HTTP-сервер с проверкой доступности и идемпотентным созданием. Оба биндинга используют одинаковую серверную семантику. Google Calendar, OAuth и внешняя база не становятся обязательными условиями запуска примеров.

### Миграция с `0.1.x`

1. Обязательный `TimeSlot.id` и правила его устойчивости.
2. Замена `BookingDetails` типизированными `values`; удаление `validateDetails` из публичного API.
3. Разделение `AvailabilityAdapter` и `BookingAdapter`, discriminated union конфигурации по `mode`.
4. Передача контекста во все запросы и событие `onContextChange`.
5. Обязательный `idempotencyKey`, объединение capabilities, категории ошибок и `resolveAttempt`.
6. Обязательные `BookingResult.id` и `status` с пояснением назначения идентификатора.
7. Новые поля результата: приглашение, место, инструкции и ссылки.
8. Формат `{ snapshot, actions }` для React hooks; удаление прямых Context-экспортов и публичного reducer API.
9. Различие между сбросом сценария и разрешением попытки; шаг `attempt`, часть `Attempt`, `startedAt` и восстановление `initialAttempt`.
10. Фиксированный режим controlled/uncontrolled и его диагностика; пары `default*` / `on*`; `TimeFormat` без режима `locale`.
11. Новые ключи `SlotlineMessages`.
12. Закрытый список причин `SelectionChangeReason` и общая форма метаданных `BookingChangeMetadata`.
13. Правила приоритета токенов раскладки: `--sl-width`, `--sl-width-adaptive`, `--sl-max-height`, `data-sl-layout`.

### Проверка раскладки

`check-layout` перестаёт ожидать ровно четыре элемента. Галерея размечает случаи явными атрибутами режима, шага и компоновки. Фиксированное ожидание четырёх шагов больше не используется ни для галереи, ни для индикатора прогресса.

## 10. Критерий завершения каждой возможности

Возможность считается завершённой, когда:

- Определены её публичный контракт и поведение по умолчанию.
- Общая логика реализована в core.
- React и Angular предоставляют эквивалентные возможности.
- Проверены ошибки, внешние обновления и жизненный цикл.
- Есть законченный пример использования.
- Добавлены документация, changeset и миграция при необходимости.
- Упакованные библиотеки проходят проверку в отдельных приложениях.
